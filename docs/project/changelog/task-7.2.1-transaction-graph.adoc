TinkerGraph 3.8.x introduced `TinkerTransactionGraph`, a variant of `TinkerGraph`
that adds ACID-compliant, thread-local transactions.
`TinkerCat` currently returns `false` from `supportsTransactions()`.
This task implements the transactional variant as a separate class in `jvmMain`,
leaving the existing `TinkerCat` class unchanged for users who do not need transactions.

== Background

=== TinkerGraph 3.7.x Behaviour

In TinkerGraph 3.7.x, `supportsTransactions()` returned `false` for the standard
`TinkerGraph` and transactions were only available through a separate, experimental
`TinkerTransactionGraph` that was not widely advertised.

=== TinkerGraph 3.8.x Changes

TinkerPop 3.8.x stabilised and documented `TinkerTransactionGraph` as the canonical way
to obtain transaction semantics from the in-memory reference graph.
It provides:

* Thread-local transaction state — writes in one thread are invisible to other threads
  until committed.
* `tx().open()` / `tx().commit()` / `tx().rollback()` — explicit lifecycle control.
* `tx().close()` — releases resources and rolls back any open transaction.
* `onReadWrite` and `onClose` callbacks for framework integration.

== Implementation Plan

=== 1. `TinkerTransactionGraph` Class

Create `src/jvmMain/kotlin/.../structure/TinkerTransactionGraph.kt`.

[source,kotlin]
----
class TinkerTransactionGraph private constructor(
    configuration: Map<String, Any?>
) : TinkerCat(configuration) {

    override fun features(): Graph.Features = TinkerTransactionFeatures()

    override fun tx(): Transaction = threadLocalTx.get()

    private val threadLocalTx = ThreadLocal.withInitial { TinkerTransaction(this) }

    companion object {
        fun open(): TinkerTransactionGraph = open(emptyMap())
        fun open(configuration: Map<String, Any?>): TinkerTransactionGraph =
            TinkerTransactionGraph(configuration)
    }
}
----

=== 2. `TinkerTransaction` Implementation

[source,kotlin]
----
class TinkerTransaction(private val graph: TinkerTransactionGraph) : Transaction {

    private var state: TransactionState = TransactionState.CLOSED

    // Snapshot of the graph at open() time — used for rollback
    private var snapshot: GraphSnapshot? = null

    override fun open() {
        check(state == TransactionState.CLOSED) { "Transaction already open" }
        snapshot = graph.takeSnapshot()
        state = TransactionState.OPEN
    }

    override fun commit() {
        checkOpen()
        snapshot = null
        state = TransactionState.CLOSED
    }

    override fun rollback() {
        checkOpen()
        graph.restoreSnapshot(snapshot!!)
        snapshot = null
        state = TransactionState.CLOSED
    }

    override fun close() {
        if (state == TransactionState.OPEN) rollback()
    }

    override fun isOpen(): Boolean = state == TransactionState.OPEN

    private fun checkOpen() =
        check(state == TransactionState.OPEN) { "Transaction is not open" }
}

enum class TransactionState { OPEN, CLOSED }
----

=== 3. Graph Snapshot Mechanism

Transactions use a copy-on-write snapshot of vertex and edge maps at `open()` time.
On `rollback()`, the graph's maps are replaced from the snapshot.

[source,kotlin]
----
internal data class GraphSnapshot(
    val vertices: Map<Any, TinkerVertex>,
    val edges: Map<Any, TinkerEdge>,
    val currentId: Long
)

internal fun TinkerTransactionGraph.takeSnapshot(): GraphSnapshot =
    GraphSnapshot(vertices.toMap(), edges.toMap(), currentId)

internal fun TinkerTransactionGraph.restoreSnapshot(snapshot: GraphSnapshot) {
    vertices.clear(); vertices.putAll(snapshot.vertices)
    edges.clear(); edges.putAll(snapshot.edges)
    currentId = snapshot.currentId
    // Rebuild all indexes from restored state
    rebuildAllIndexes()
}
----

NOTE: The copy-on-write approach is appropriate for the reference implementation
and graphs with up to ~100K elements.
A full MVCC implementation is planned as a future enhancement.

=== 4. Thread Safety

Each thread holds its own `TinkerTransaction` via `ThreadLocal`.
Uncommitted writes in one thread are immediately visible to other threads
(last-writer-wins).
The transaction provides rollback capability only — it does not provide snapshot
isolation between concurrent writers.
Applications requiring strict isolation must synchronise at a higher level.

=== 5. Feature Flags

[source,kotlin]
----
private class TinkerTransactionFeatures : TinkerCatFeatures() {
    override fun graph() = object : TinkerCatGraphFeatures() {
        override fun supportsTransactions() = true
        override fun supportsThreadedTransactions() = false
    }
}
----

=== 6. `JvmPersistenceLayer` Integration

`TinkerTransactionGraph` cooperates with the existing `JvmPersistenceLayer`:
persistence operations (`saveToFile`, `loadFromFile`) require an open transaction
and commit automatically on success.

=== 7. Usage Example

[source,kotlin]
----
val graph = TinkerTransactionGraph.open()
val tx = graph.tx()

try {
    tx.open()
    val alice = graph.addVertex("label", "person", "name", "Alice")
    val bob   = graph.addVertex("label", "person", "name", "Bob")
    alice.addEdge("knows", bob)
    tx.commit()
} catch (e: Exception) {
    tx.rollback()
    throw e
}
----

Or with Kotlin's `use`:

[source,kotlin]
----
graph.tx().use { tx ->
    tx.open()
    graph.addVertex("label", "person", "name", "Alice")
    tx.commit()
}
----
